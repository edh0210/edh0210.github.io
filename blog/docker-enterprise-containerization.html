Contenerización de Aplicaciones Enterprise con Docker

Más allá de 'docker run': Patrones de ingeniería para empaquetamiento inmutable, builds multi-etapa seguros, orquestación y pipelines CI/CD de producción.

👤 EDH // Edwin Hernández
⏱️ 11 min read
🏷️ Docker / DevOps / Multi-Stage / CI/CD

1. De 'Funciona en mi Máquina' a Entornos Inmutables

El empaquetamiento tradicional de software dependía de la instalación manual de dependencias, variables del sistema operativo y servidores de aplicaciones configurados a mano. Esta falta de determinismo era la causa principal del síndrome 'funciona en mi máquina local pero falla en producción'.

3. Builds Multi-Etapa (Multi-Stage Builds) de Producción

Incluir herramientas de compilación (compiladores, SDKs, código fuente raw) en la imagen final de producción incrementa exponencialmente el tamaño y la superficie de ataques de seguridad. La solución técnica son los Multi-stage builds:

Dockerfile 
# STAGE 1: Compilation & Build Environment
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build-env
WORKDIR /src

# Copy project definition and restore dependencies (Caching layer)
COPY *.csproj ./
RUN dotnet restore

# Copy all source code and compile optimized production release
COPY . ./
RUN dotnet publish -c Release -o /app/out

# STAGE 2: Minimal Production Runtime Environment
FROM mcr.microsoft.com/dotnet/aspnet:8.0-alpine AS runtime-env
WORKDIR /app

# Security: Create non-root user
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# Copy only the compiled binaries from Stage 1
COPY --from=build-env /app/out ./

EXPOSE 8080
ENV ASPNETCORE_URLS=http://+:8080

ENTRYPOINT ["dotnet", "EnterpriseApp.dll"]

4. Orquestación Multi-Contenedor con Docker Compose

Para simular el ecosistema enterprise de producción en entornos locales, utilizamos docker-compose.yml definiendo redes aisladas, volúmenes de persistencia y dependencias de inicio (depends_on):

YAML (docker-compose.yml) 
version: '3.8'

services:
  web-api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8080:8080"
    environment:
      - ConnectionStrings__Database=Server=db;Database=EnterpriseDB;User Id=sa;Password=${DB_PASSWORD};
      - Redis__Configuration=cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    networks:
      - backend-network

  db:
    image: mcr.microsoft.com/mssql/server:2022-latest
    environment:
      - ACCEPT_EULA=Y
      - MSSQL_SA_PASSWORD=${DB_PASSWORD}
    volumes:
      - sql-data:/var/opt/mssql/data
    healthcheck:
      test: ["CMD-SHELL", "/opt/mssql-tools/bin/sqlcmd -S localhost -U sa -P ${DB_PASSWORD} -Q 'SELECT 1'"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - backend-network

  cache:
    image: redis:7-alpine
    networks:
      - backend-network

networks:
  backend-network:
    driver: bridge

volumes:
  sql-data:

6. Prácticas de Seguridad en Contenedores

  • Non-Root User: Nunca ejecute contenedores como usuario root. Defina siempre un usuario no privilegiado en la directiva USER.
  • Minimal Runtime Base Images: Prefiera distribuciones ultra livianas como Alpine Linux o imágenes Distroless para reducir vulnerabilidades CVE.
  • Secrets Isolation: Nunca incruste contraseñas, tokens JWT o claves de API dentro de las capas del Dockerfile. Utilice variables de entorno inyectadas en tiempo de ejecución.
  • Image Tag Pinning: Evite usar el tag latest en producción. Especifique siempre versiones explícitas e inmutables (ej. redis:7.0.12-alpine).

7. Checklist de Contenerización Enterprise

☑ [ ] Implement Multi-Stage Builds (Separate Build & Runtime)
☑ [ ] Enforce Non-Root Execution (USER appuser)
☑ [ ] Pin Base Image Versions (Avoid :latest tag)
☑ [ ] Inject Secrets via Environment / Vault (No Secrets in Layers)
☑ [ ] Configure HEALTHCHECK Probes (Liveness & Readiness)
☑ [ ] Use Managed Docker Volumes for Stateful Storage
☑ [ ] Isolate Container Networks via Bridge Driver
☑ [ ] Automated Vulnerability Scanning in CI/CD Pipeline
